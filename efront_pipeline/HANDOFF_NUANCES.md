# eFront Pipeline — Knowledge Transfer: Business Logic & Control Nuances

**Purpose:** This document is NOT a code walkthrough — it captures the tribal knowledge, business rules, and control mechanisms behind the `efront_pipeline` that a new engineer cannot get just by reading the code casually. Read this alongside the codebase, not instead of it.

**Pipeline shape:** `ingestion → landing → bronze_layer → silver_layer → gold_layer`, plus a standalone `cdm_checker` audit tool (**no longer used** — see §6) and `efront_specific` historic-backfill utilities. Every layer has a **manual** and a **scheduled** parameter set (see §9) driving the same load code down different table lists/cadences.

---

## Quick Overview — the ingestion process at a glance

*A refresher for someone who already knows the pipeline, not a replacement for the detailed sections below.*

1. **Ingestion (eFront API → landing):** for each table, log in to eFront Cloud (Basic auth, shared `OEGENAPI` service account) → single GET → log out. Raw JSON is column-sanitised and blank rows dropped, then landed.
   - **Scheduled set** (~16 reference/master tables — company, fund, transactions, etc.): runs hourly, 06:20–18:20 UTC, `save_mode: overwrite`.
   - **Manual set** (`aum_asset`, `aum_fund`): triggered by hand only, because the eFront API has no "submit" barrier and would otherwise pull unfinalised draft data. Uses `save_mode: merge` with a scoped delete keyed on `REPORT_DATE`, so re-running just replaces that quarter without touching prior quarters.
2. **Bronze layer (landing → typed/validated):** a DLT pipeline (manual and scheduled variants) applies hard/soft data-quality rules per table (future-dated checks, blank-field checks, etc.). Hard-check failures go to a `quarantine` table and are excluded from the clean output; soft-check failures are just flagged. Always a full refresh — bronze is rebuilt every run, never incremental. No cross-table/referential checks happen here.
3. **Silver layer (bronze → business-modeled):** the core business logic layer. Every relevant entity is left-joined against the company's **Core Data Model (CDM)** to prove it's a registered fund/company/portfolio — unmapped entities on a **hard** check are quarantined and silently drop out of reporting; **soft** checks just flag. This layer also does FX conversion to GBP, calendar gap-filling, transaction classification, and the AUM-specific portfolio-level rollups (country/technology grouping, fund-of-funds elimination rows, "N/A" bodge mappings for non-CDM portfolios like "Undeployed").
4. **Gold layer (silver → reporting-ready):** builds KPIs and views in a strict dependency order (views first, then level-1 tables from silver, then level-2 tables/variants that read level-1 outputs) — most notably the **AUM Bridge View**, a period-over-period reconciliation from `Previous_AUM` to `Current_AUM`. Manual = the AUM family + views; scheduled = the FundOperations/track-record family.
5. **Downstream publishing (DataHub):** reaching the gold tables isn't the same as being visible to everyone. A separate DataHub control (`efront_publishing_control`) gates AUM visibility — validation users see new data immediately, but general users only see up to whatever quarter was last manually marked as the "latest visible report date." This is a manual publishing step, distinct from the pipeline run itself.
6. **Supporting mechanisms running alongside the main flow:**
   - **Manual vs scheduled** parameter sets exist at *every* layer (ingestion, bronze, silver, gold) — same code, different table lists/cadences.
   - **Historic backfill/union** (`efront_specific/`) merges one-time pre-pipeline historic data (sourced from a SharePoint spreadsheet → CSV → Volume) with the ongoing API-ingested tables, self-healing if a historic table is missing.
   - **CDM Checker** is a legacy, manually-run audit notebook — **no longer used**, kept only for historical context (§6).

For the "why" behind any of these steps, the hardcoded values, the known gotchas, and the things that break silently — see the detailed sections below.

## 1. The CDM Mapping Validation Pattern (the thing you specifically asked about)

**Why it exists:** eFront is just one source system. The **Core Data Model (CDM)**, in catalog `oegen_data_prod_prod.core_data_model`, is the company's canonical cross-system reference for funds/companies/portfolios. Before any eFront entity is trusted into shared reporting, the pipeline proves it's registered in the CDM — otherwise unreconciled, duplicate, or mistyped entities could silently pollute BI numbers (AUM, NAV, etc.).

**eFront's identity in the CDM:** the source system is registered under `source_system_id = 'SRCE_SYST_1001'`. This literal string is hardcoded and duplicated across many files (silver join checks, CDM checker SQL, gold transaction mapping) — **there is no shared constant for it**. If eFront's registration ID ever changes, every occurrence must be found and updated by hand.

**The CDM mapping tables** (all live in `oegen_data_prod_prod.core_data_model`, NOT in the efront catalog/schemas):
- `bronze_mapping_fund` — keyed by `source_fund_id`
- `bronze_mapping_company` — keyed by `source_company_id`
- `bronze_mapping_portfolio` — keyed by `source_portfolio_id`
- `bronze_mapping_system_sources` — registry of valid source systems (filtered `WHERE END_AT IS NULL` for active ones only)

Each mapping table is deduplicated to "latest row per source ID" via `ROW_NUMBER() OVER (PARTITION BY source_<entity>_id ORDER BY last_updated DESC)` — always take `rn = 1`.

**How the check works (silver layer — the automated, in-pipeline version):**
1. `silver_layer/silver_sql_join_checks/_fund_with_no_mapping_to_cdm.py` (and the `_company_...`, `_portfolio_...`, `_source_system_id_...` siblings) each define a SQL query pulling the relevant CDM mapping table filtered to `source_system_id = 'SRCE_SYST_1001'`.
2. Each silver table's parameter config (`silver_table_parameters_manual.py` / `_scheduled.py`) declares a `sql_join_checks` dict wiring a specific column (e.g. `ef_fund_id`) to the CDM check's key (`source_fund_id`), and marks it `hard_check: True` or `False`.
3. `silver_dlt_load.py` calls `apply_sql_left_join_checks` → `process_sql_left_joins` (in `common/funcs/dlt_helper.py`), which runs the CDM reference query, broadcasts it, and does a **LEFT JOIN** from the silver dataframe onto it.
4. Where the CDM-side key comes back **NULL** (no match), a flag column `DQ_hard_{check_name}` or `DQ_soft_{check_name}` is set to `1`.

**What happens when it fails:**
- **Hard check failure** → row is routed to a `quarantine` DLT table and **excluded** from the clean/final table (`filter_quarantine_clean` computes `DQ_hard_quarantine = greatest(...)` across all hard flags). This means an unmapped fund/company/portfolio literally disappears from reporting output — not a warning, a silent drop (though it's logged, see below).
- **Soft check failure** (e.g. `_rows_with_missing_fields_check`, used only on `aum_metrics_enriched`) → flagged but the row stays in the clean output. Informational only.
- Every table's quarantine stats (row counts, hard/soft counts, timestamps) roll up into one monitoring table: `{TARGET_TBL_PREFIX}quarantine_union_{PIPELINE_TYPE}` — **this is the one place to check for CDM mapping drift across the whole pipeline.**

**Documented exception — read this before "fixing" it:** `_investor_in_fact_table_but_not_dim_table.py` is enabled as a **hard** check on `fundoperations_by_investor`, but is explicitly commented OUT for `fundoperations_daily`/`monthly`/`quarterly` in `silver_table_parameters_scheduled.py`, with the inline comment *"investor account is sometimes in left but not in right in eFront cos no enforced key rules."* This is a deliberate relaxation, not a bug — eFront doesn't enforce referential integrity between fact and dimension investor accounts, and those three tables would otherwise lose legitimate rows.

**The standalone CDM Checker tool was a *different*, manual thing — don't confuse the two, and note it's no longer used.** See §6.

## 2. Ingestion Layer (eFront API → landing zone)

- **Source system:** BlackRock eFront Cloud, oegen's specific tenant at `https://oegen.efrontcloud.com` (hardcoded). Auth is HTTP Basic against a shared service account `OEGENAPI`, password from Databricks secret scope `XIO` / key `blackrock_efront_api_password`.
- **Session pattern:** login → single GET → logout, **per table, per call** — not one session reused across ~16 tables. This is almost certainly to avoid the vendor system throttling/locking a shared service account from too many concurrent sessions.
- **Table → endpoint map (manual set, `save_mode: overwrite`):** `company`, `datapointsexport`, `fees_company`, `fees_fund`, `fund`, `fundoperations`, `fx`, `investor`, `investoraccount`, `instruments`, `ownership`, `track_record_fund_quarterly_snapshots`→`/track_record_fund_updated`, `track_record_investor_quarterly_snapshots`→`/track_record_investor_updated`, `track_record_asset_quarterly_snapshots`→`/track_record_asset_updated`, `transactions`, `transactions_paid`. To add a new eFront table, you add both the endpoint path here and decide overwrite vs merge (see below).
- **Table → endpoint map (scheduled set, `save_mode: merge`):** only `aum_fund_quarterly_snapshots`→`/aum_fund` and `aum_asset_quarterly_snapshots`→`/aum_asset`. These merge with `delete_mode='scoped'` and a `period_column` (`REPORT_DATE`) + `match_keys` (fund: `REPORT_DATE`+`FUND_SHORT`; asset: `+PORTFOLIO_NAME`+`COMPANY_NAME`) — meaning if eFront retroactively removes/corrects a fund or asset from a historical quarter, the scoped delete removes the corresponding old row.
- **Cadence:** scheduled (master/reference) tables run **hourly, 06:20–18:20 UTC daily** in prod (weekly Sunday in staging). The AUM endpoints (`aum_asset`, `aum_fund`) are **not on this schedule at all** — they are triggered on demand only. See below for why.
- **Why AUM ingestion is manual, not scheduled:** the eFront API has **no "submit" barrier**. If `aum_asset`/`aum_fund` were pulled on an automated schedule, the API would return **draft data** the instant the Fund team starts entering it into the eFront UI — before it's been reviewed or finalised. Ingesting draft data feeds directly into the AUM models and **corrupts the AUM reporting page in DataHub** (the downstream BI tool consuming this pipeline). To avoid this, these two endpoints are pulled manually, and only once the Fund team confirms the current quarter's data is finalised.
- **The manual AUM ingestion workflow (do this every quarter):**
  1. **Confirm the Report Date.** Each run of `aum_asset`/`aum_fund` returns data for whichever quarter is *currently selected* in the eFront UI — there's no parameter to pick a specific quarter from the API side. Before pulling anything, ask **Daniel O'Brien or Amanda Foon** which report date/quarter is currently selected in eFront.
  2. **Run the ingestion.** Once given the green light, trigger the manual pull. It's safe to re-run as many times as needed — you can keep pulling until the Fund team confirms the data for that quarter is fully finalised (each re-run simply re-merges the latest state, see below).
  3. **How the data merges.** Both endpoints land in `aum_fund_quarterly_snapshots` / `aum_asset_quarterly_snapshots` via the `save_mode: merge` / `delete_mode: scoped` mechanism already described above. In practice this means: the new pull **replaces all existing data for that specific quarter** (identified by `REPORT_DATE` in `match_keys`); all previously ingested data for **prior** quarters is left untouched/retained. Much older historic data (pre-pipeline) is kept safely in a separate volume — see §8's historic backfill mechanism, which is a distinct thing from this quarterly MERGE.
- **Column sanitisation** (`BlackRockEFrontAPI.sanitise_column_names`): fixed, ordered character replacements for Spark-illegal characters from eFront's raw headers: `( )→_`, `.`/`~`/`:`→removed, `%`→`perc`. Order matters and there's no double-underscore collapsing — a header can end up `Foo__Bar`.
- **Row filtering:** `dropna(how="all")` happens **before** the ingestion timestamp column is added, and the notebook additionally pre-filters raw JSON rows where every value is null/blank before even creating the Spark DataFrame — a defense against blank padding rows eFront's export apparently returns.
- **Schema drift risk:** manual (overwrite) tables have no `column_order`/`match_keys` and rely on `overwriteSchema=true` — a renamed eFront column silently appears as a new column with zero alert.

## 3. DataHub Visibility & Publishing Controls (why a manual AUM pull isn't visible to everyone straight away)

This isn't part of the eFront pipeline's code at all, but it's the reason §2's manual workflow exists and it trips people up if they don't know it — so it belongs here.

**The problem this solves:** once you've manually pulled AUM data (§2), that data is sitting in `aum_fund_quarterly_snapshots`/`aum_asset_quarterly_snapshots` and flows through to DataHub — but it should not be shown to everyone the instant it lands, because it hasn't been validated yet. DataHub therefore has its own **two-tiered visibility control**, separate from anything in this codebase:

- **Special Users (Validation):** see newly pulled AUM data in DataHub **immediately**. This lets a small validation group check the numbers/visuals look right before anyone else sees them.
- **General Users:** only ever see AUM data **up to the "latest visible report date"** — i.e. general users are frozen on whatever quarter was last explicitly published, even if a newer quarter has already been pulled and is sitting in the tables.

**How to publish a newly validated quarter to General Users:** an authorized user must update the **"latest visible report date"** setting. This is a manual step — pulling the data (§2) does **not** automatically publish it.
- **UI location:** Streamlit DataHub UI → **Data Management** (left-hand menu) → **eFront Configuration**.
- **Backend:** that UI control writes to the Databricks table `oegen_data_prod_prod.oegen_apps.efront_publishing_control`.

**Practical implication for whoever takes this over:** if someone reports "the new quarter's AUM numbers aren't showing up in DataHub" after a manual pull has been run and confirmed finalised, the fix is very likely *not* a pipeline bug — check whether the "latest visible report date" has actually been bumped in eFront Configuration first.

## 4. Bronze Layer (landing → validated/typed bronze)

- **Two DLT pipelines, one notebook:** `bronze_dlt_load.py` reads Spark confs `xio.table_parameters_module` and `xio.pipeline_type` to decide whether it's running the manual or scheduled table set. Both bronze DLT pipelines run with `full_refresh: true` unconditionally — **bronze is fully rebuilt every run**, never incremental.
- **Quarantine is NOT a hard pipeline failure by default.** Despite `bronze_table_rules.py` looking like `@dlt.expect_or_drop` candidates, they're implemented manually: `apply_custom_hard_checks` writes `DQ_hard_<rule>` flag columns, then `filter_quarantine_clean` splits rows into a `clean_` table (used downstream) and a `quarantine_` table (unioned across all bronze tables into `{TARGET_TBL_PREFIX}quarantine_union_{PIPELINE_TYPE}`). **The only true hard-fail in bronze** is `enforce_uniqueness_expectations`, which uses a real `@dlt.expect_or_fail` on duplicate keys — if a configured uniqueness key set has dupes, that run fails outright.
- **Rule inventory and business meaning:**
  - `aum_asset`/`aum_fund`: `future_REPORT_DATE` — an AUM-as-of date can't be in the future.
  - `company`/`fund`/`instruments`/`datapointsexport`: future-dated `Created_on`/`Modified_on`/audit timestamps — corrupt source metadata guard.
  - `fundoperations`: blank-tolerant future-date checks (`OR TRIM = ''`) plus empty-string checks on `Currency`, `Draft`, `Fund`, `Fund_IQId`, `Investor_Account`, `Share`, `Short_Name`, `Transaction_Investor_IQId`, `Type` — a capital call/distribution row is unusable without these.
  - `track_record_asset`: `negative_MOIC` — MOIC below 0 is not economically meaningful.
  - `track_record_fund`: `negative_WEIGHTED_YIELD_UNITS`.
- **Fund-acting-as-investor carve-out (`investoraccount` rules):** in eFront, a fund can itself appear as an "Investor" in another fund's cap table (fund-of-funds structures). Such synthetic rows naturally have blank `Country`/`Fund_IQId`/etc. Rather than flag these as bad data, the empty-field rules are guarded by `AND Investor NOT IN (SELECT Fund FROM {LANDING_DB}.{PREFIX}fund)` — i.e., skip the check if the "Investor" is actually a known Fund name. This is a live cross-table subquery against the pre-bronze landing `fund` table, re-evaluated every run — brittle if `PREFIX`/schema naming ever diverges.
- **Dead/disabled rules to be aware of:** `track_record_asset`'s rule exists in `bronze_table_rules.py` but the table is commented out of `bronze_table_parameters_scheduled.py` — it currently never runs. `investoraccount` and `fundoperations` have `uniqueness_expectations` commented out despite having natural keys — duplicates in these tables are NOT hard-failed today.
- **No join/referential checks exist at bronze.** `bronze_sql_join_checks/` contains only an empty `__init__.py` — the left-join CDM-style validation only happens at silver (§1). Orphaned foreign keys at bronze pass through undetected.
- **Manual vs scheduled bronze:** manual = only `aum_asset`/`aum_fund` (the AUM feed, uploaded separately from the API sync); scheduled = everything else (company, fund, fundoperations, fx, instruments, investoraccount, investor, ownership, track_record_fund, transactions, transactions_paid, fees_company, fees_fund, datapointsexport). SCD2 is configured `False` everywhere — the SCD2 code path exists but is unused today.

## 5. Silver Layer (bronze → business-modeled, CDM-validated)

Beyond the CDM mapping pattern in §1, this layer holds most of the actual PE-domain business logic:

- **Calendarisation (`silver_fundoperations_*_calendarised.py`):** builds a synthetic calendar spine per grouping combo from first activity to the **global** max period across ALL combos (not just that combo's own last date) via `SEQUENCE`/`EXPLODE`. Flow columns (Commitments/Called/Distribution) are zero-filled for generated gap periods; the NAV **stock** column is forward-filled (`LAST_VALUE(NAV, true) OVER (...)`). The by-type/by-country variants group by `Investor_Type`/`Investor_Country` (`COALESCE(..., 'Unknown')`) and **omit NAV forward-fill** since NAV doesn't exist at that grain. **Outlier:** `silver_fundoperations_by_investor.py` does NO gap-filling at all — just a straight cumulative sum ordered by `Effective_Date`, so investor-level history gaps are left as-is, inconsistent with every other rolled-up table.
- **FX conversion (`silver_fx_vs_gbp.py`):** hardcoded 10-currency map (GBP, EUR, USD, AUD, SEK, PLN, NOK, JPY, KRW, CAD), matched by currency **name** not ISO code. Computes both `fx_direct` (source→GBP) and `fx_inverse` (GBP→destination, `1.0 / Fx_Rate`) as separate branches, unioned. GBP-to-GBP is never emitted as a row — downstream consumers must assume an implicit 1.0 rate for GBP. **Adding an 11th currency requires updating `curr_map` or it silently vanishes from output with no error.**

**What it does (while it's still live):** blends two eFront sources into one fund-level performance metric feed — the dedicated `track_record_fund` bronze table (eFront's own pre-calculated IRR/MOIC/DPI/yield metrics) and `datapointsexport` (raw datapoints for 6 additional metrics: Total Shareholder/NAV Return and their annualised variants, Annualised Dividend Paid, Weighted Average Discount Rate). These are joined to CDM fund identity, unpivoted into one `(fund, metric, date, value)` shape, then re-pivoted into year columns (Dec-31 snapshots only) plus a "latest value" column pair.

**The two CDM control tables the user should know about** (both in `oegen_data_prod_prod.core_data_model`, i.e. not eFront-specific — shared reference data):
- **`ref_metric_display_name_mapping`** — maps each normalised `raw_metric` key (e.g. `net_cagr`) to the human-readable `display_name` shown in DataHub (e.g. "Net CAGR"). Used in both `silver_track_record_metric_dictionary.py` and `silver_track_record_fund.py`. Same gotcha as everywhere else in this pipeline: a new upstream metric with no row here just gets a blank/NULL display name — no error.
- **`ref_track_record_metric_visibility`** — *intended* to control, per `domain` (e.g. `'fund'`) and an `is_visible` flag, which metrics are actually allowed to surface for reporting — i.e. which metrics get shown for which context. **Important gotcha to flag to your teammate:** this filter is only ever applied in the **old, disabled notebook version** of the model (`silver_track_record_fund.ipynb`) — that notebook is commented out of `silver_model_parameters_scheduled.py` and hasn't run in any active job since the model was rewritten as plain SQL (`silver_track_record_fund.py`, introduced in the same commit that also moved `fx_vs_gbp` off notebooks). **The active `.py` SQL version never applies this visibility filter at all** — it joins `ref_metric_display_name_mapping` for display names only. So today, `ref_track_record_metric_visibility` is not actually gating anything live in the pipeline, even though its name and the surviving notebook code strongly suggest it should be — treat any assumption that "visibility is controlled by that table" as currently false until someone re-wires it (or decides not to, given the retirement risk above).
- **`silver_track_record_metric_dictionary.py`** itself hardcodes 12 metric names + 18 manually-authored definitions, joined to `ref_metric_display_name_mapping` for display names. `silver_track_record_fund.py` hardcodes `years = range(2000, 2036)` for the pivot column list (with a comment noting to extend the range) — **will silently truncate data for any fund reporting past 2035.**

### `silver_aum_metrics_enriched.py` — **this is a KEY dataset**, read this whole bullet before touching it

This model doesn't just enrich the AUM feed — it **groups/aggregates asset-level data up to the investment-portfolio level**, because portfolio is the level at which AUM is reported. That rollup requires several bespoke, eFront/AUM-specific rules that don't exist anywhere else in the pipeline:

- **`_ref_country_groupings` / `_ref_tech_groupings`** — two bespoke reference tables (in the landing schema) that exist *only* for eFront AUM reporting. They group individual raw countries/technologies (as recorded per asset in eFront) into the coarser categories actually used for reporting. They're joined in per-asset before the portfolio-level rollup, then collapsed further:
  - **Country rollup rule:** after applying `_ref_country_groupings`, if the resulting set of grouped country names for a portfolio has **more than 1 distinct value**, the reporting country column is collapsed to **`'Multi-Country'`**. If it collapses to exactly 1, that's the reporting country. There's also a specific named-portfolio override: for `cdm_portfolio_id = 'INVP_1132'`, if the underlying assets are in both Portugal and Spain, the reporting country is forced to `'Spain'` (not `'Multi-Country'`) — a deliberate one-off exception, not a bug.
  - **Technology rollup rule (parallel logic, same idea):** after `_ref_tech_groupings`, if a portfolio's technologies collapse to exactly one grouped combination consisting of some renewable tech **plus** `'Battery storage'`, the label becomes `"<Tech> & Battery storage"` (e.g. `"Solar & Battery storage"`). If there are 2+ distinct grouped technologies and it's *not* that specific battery-storage-pairing case, it collapses to **`'Multi-Tech Renewables'`**.
  - Both rules only kick in when there's a genuine multi-value case *after* grouping — a portfolio with one grouped country/technology just reports that value directly, unchanged.
- **`'Undeployed'` portfolios and other non-legitimate portfolios (the `n/a_` bodge mapping mechanism):** some portfolios that need to appear in the AUM output **aren't real CDM-registered investment portfolios** — `'Undeployed'` capital being the main example, plus a few fund-of-funds sub-portfolios (see elimination rows below). Since §1's silver CDM mapping left-join check would otherwise **quarantine and drop** any portfolio ID that has no CDM mapping, these get a deliberate **bodge mapping row added to the CDM mapping table** (`bronze_mapping_portfolio`) with a **fake ID prefixed `n/a_`** (e.g. `n/a_Sustainable_Growth_Fund_Equities`, `n/a_Sustainable_Growth_Fund_Investment_Trusts`, `n/a_Undeployed`). **This is the whole point of the bodge: it makes these fake portfolios "mapped," so they pass the left-join check in §1 instead of being quarantined.** Once past that check, `silver_aum_metrics_enriched.py` then explicitly overrides a run of asset-attribute columns (fund/portfolio names, strategy, sector, etc.) to the literal string `'N/A'` for any row where `ef_portfolio_id` starts with `n/a_` (or is `'Undeployed'`, or is one of a few other specifically listed IDs like `INVP_1007`/`INVP_1160`–`1162` under fund `FUND_1017`) — so downstream reporting shows a clean `'N/A'` rather than a fake business-looking value.
- **Fund-of-funds elimination rows:** for the SGF sub-portfolios under fund `FUND_1017` (the fund-of-funds structure), the model adds **extra negated rows** (every AUM/NAV/GAV/cash-flow metric column multiplied by -1) via `UNION ALL`, tagged with dedicated `n/a_elimination_bodge_sgf_*` IDs and display names suffixed `' [ELIMINATION]'`. These exist purely **to cancel out double-counting** when the sub-portfolio's AUM is rolled up to the fund or OEGEN-wide total — without them, capital already counted at the sub-portfolio level would be counted again at the parent level.
- Every asset-attribute column in this model is also **forward-filled** per fund+portfolio across report dates (carry the last known value forward if the current period is NULL), with a `backfilled` audit flag set wherever a value had to be carried forward rather than reported fresh that period.
- **Transactions vs transactions_paid:** `silver_transactions.py` is the accrual-basis ledger; `silver_transactions_paid.py` is the cash-settlement counterpart (distinct `date_paid`/`amount_paid`, composite key `[transaction_id, date_paid]`). Both feed `silver_aggregated_asset_transactions.py`, which classifies cashflow type via a hardcoded 12-entry lookup (e.g. `'EQ - Conversion in' → 'Injections'`) — **any new/renamed eFront transaction type silently produces a NULL cashflow_type with no error.**
- **Other magic values to know about:** `'Top 20'` share exclusion in `silver_fundoperations_raw.py`; a near-zero row drop `ABS(...) < 0.005 AND PORTFOLIO_NAME != 'Undeployed'` in `silver_aum_metrics.py`; string-matched transaction type labels (`'MF: Call'`, `'MF: Net Asset Value'`) in `silver_fundoperations_daily.py`; shareholder-loan detection via `LOWER(description) LIKE '%credit facility loan%'` in `silver_aggregated_asset_transactions.py`.
- **Manual vs scheduled silver:** only `aum_metrics` and `aum_metrics_enriched` are in the manual parameter set — everything else is scheduled.

## 6. The CDM Checker — ⚠️ NO LONGER USED (kept here for historical/reference context only)

**Do not confuse this with §1**, and don't assume it's part of the active pipeline shape — it isn't. The silver-layer CDM checks in §1 run *inline*, automatically, inside the DLT pipeline, and quarantine/drop bad rows as part of normal operation; that's the live, load-bearing mechanism. The **CDM Checker** (`cdm_checker/cdm_checker_code.ipynb`) was a **separate, manually-triggered notebook**, meant for a human (data steward/analyst) to spot-check CDM mapping completeness — e.g. before/after a CDM mapping update, or when investigating a discrepancy. It never gated anything; it just produced audit tables for a person to read, and **it is no longer in active use.** The section below is retained so whoever inherits this pipeline understands what it was and why it's still in the repo, in case anyone asks about it or considers reviving it — not because it needs to be maintained going forward.

- **Config-driven:** `cdm_checker_configuration.py` defines six checks (`aum_funds`, `aum_companies`, `aum_portfolios`, `raw_funds`, `raw_companies`, `raw_portfolios`) plus a `summary_table` output location. Each entry specifies a `Data` source (an eFront-side SQL query) and a `CDM` source (a SQL query or table), a `join_type: left`, and `join_columns` split into:
  - **primary** — the actual CDM mapping ID join (e.g. `MAPPED_CDM_FUND_ID` ↔ `fund_core_id`) that determines match/no-match.
  - **secondary** — columns NOT used in the join; compared row-by-row *after* the join to flag attribute drift where the ID matched but underlying details (name, address, VAT number, etc.) diverged between eFront and the CDM.
- **`aum_*` vs `raw_*`:** `aum_*` checks pull from AUM-reporting-specific fact tables (only entities that appear in AUM reports); `raw_*` checks pull from the full eFront dimension tables — a broader, more complete population check. (Note: for funds specifically, `aum_funds` and `raw_funds` happen to use the same underlying SQL files today — the fact/dim split is clearest for companies and portfolios.)
- **`SRCE_SYST_1001` reappears here too**, filtering `bronze_mapping_fund`/`bronze_mapping_company`/`bronze_mapping_portfolio` — same eFront source-system identifier as §1, hardcoded independently in these files.
- **⚠️ Important risk to flag to your teammate:** every CDM-side query and the `"table"`-type inputs (`aum_portfolios`, `raw_portfolios`) hardcode the literal catalog `oegen_data_prod_prod.core_data_model...` — bypassing the normal `DATA_CATALOG`/prefix parameterization used everywhere else in the pipeline. **This means the CDM Checker always compares against live PROD CDM data, regardless of which environment (dev/staging/prod) you run the checker notebook from.** Only the eFront-side data and the *output* location respect dev/staging prefixing. Running this "in dev" does not mean it's safe/isolated — it still reads real production CDM mappings.
- **Output:** for each of the six checks, writes a full result table to `{DATA_CATALOG}.{LANDING_SCHEMA}.{PREFIX}__cdm_checker__{check_name}` (overwrite), plus one rollup row per check into `{DATA_CATALOG}.{LANDING_SCHEMA}.cdm_checker_summary` with match/missing-in-CDM/missing-in-Data/missing-in-both counts — this summary table is the first place to look when asked "are all our eFront entities properly mapped in the CDM right now?"

## 7. Gold Layer (silver → reporting-ready KPIs and views)

- **Build order is real and encoded by filename prefix + a `level` key** in the parameter/view config files (`gold_view_parameters_manual.py`, `gold_table_parameters_manual/scheduled.py`). `gold_entry.ipynb` sorts and builds by level — **running scripts out of order will fail or silently produce empty/stale joins**, because higher-level scripts read the outputs of lower-level ones:
  - **Level 0 (views):** `0_gold_aum_capital_injections_and_disposals_transactions_view.py` (reads only silver + CDM bronze — the true root) → `0_gold_aum_bridge_view.py` (reads silver **and** the transactions view above — must run second).
  - **Level 1 (tables):** `aum_kpis`, `aum_metrics`, `fundoperations_monthly_totals`, `fundoperations_quarterly_totals`, `track_record_fund` — all read only from silver, independent of each other.
  - **Level 2 (tables):** the `_by_reporting_country/lifecycle_phase/technology` and `_vs_prev` variants read level-1 `aum_metrics`/`aum_kpis`; the investor country/type share tables read the level-1 totals tables as their % denominator.
- **AUM Bridge View — this is a standard PE reconciliation walk** from `Previous_AUM` (prior period via `LAG` over `REPORT_DATE`) to `Current_AUM`, decomposed into: `Asset_Capital_Injections`, `Asset_Disposals`, `Asset_Committed_Equity`/`Asset_Debt_Movements` (period-over-period deltas), `Fund_Level_Adj` (cash/expense/adjustment deltas), and `Asset_NAV_Change` — which is **not sourced directly, it's the plug/balancing residual** (`Current_AUM − Previous_AUM − everything else`) capturing valuation/performance movement. **Transactions the transactions-view can't match to an AUM fund+portfolio period get a NULL effective date and are silently dropped from the bridge** — they never surface as a discrepancy anywhere.
- **Capital injections/disposals classification** uses exact hardcoded `type` string matches: 4 injection types (`"EQ - Purchase/Subscription (w/o Commitment)"`, `"EQ - Subscription (Capital Issue following Commitment)"`, `"LN - Advance/Purchase (w/o commitment)"`, `"LN - Advance (following Commitment)"`) and 1 disposal type (`"EQ - Sale/Redemption"`). **Two funds have hardcoded name-to-ID overrides** because eFront's naming doesn't match the CDM: `ORIP` → `154DF9017A364F8091EBAEB00FFDE565` ("Sky"), `OEOW` → `FFA63E0C568F4DBD9730865DEAA6CB67` ("Vector"). **Known comment/code mismatch:** a comment claims "no FX rate found assumes 1.0" but the code only forces 1.0 for `currency = 'GBP'` — any other currency with no FX match returns NULL, not 1.0.
- **The `_vs_prev` pattern is NOT calendar-aware** — "previous" is just `LAG(Report_Date)` over whatever distinct dates exist in the table, not "prior quarter" specifically. If load cadence ever changes (e.g. to monthly), "prev" silently becomes prior month. Also note: `2_gold_aum_kpis_vs_prev.py` includes `Asset_NAV` in its 7 unpivoted metrics; `2_gold_aum_kpis_by_fund_vs_prev.py` only unpivots 6 metrics and **omits `Asset_NAV`** — an existing inconsistency between the two, not by design as far as anyone documented.
- **Investor share % tables** use the level-1 totals tables (`fundoperations_monthly_totals_by_fund`/`_quarterly_totals_by_fund`) explicitly as the denominator, joined on `Fund + Transaction_Currency + Year_Month/Quarter`. A header comment notes these gold scripts intentionally reprocess **full history every run** (regardless of SCD `__end_at` status), relying on a downstream MERGE to dedupe.
- **Manual vs scheduled gold:** manual = the whole AUM family (`aum_kpis`, `aum_metrics`, all `_by_reporting_*`/`_vs_prev` variants) plus the bridge/transactions views config. Scheduled = the FundOperations family (totals, investor shares, track record). **Gold views are manual-only** — the scheduled job passes an empty `view_parameters_module`, so views never rebuild on the automated cadence.
- **Undocumented columns:** `aum_kpis_by_reporting_country/lifecycle_phase/technology` and `aum_kpis_by_fund_vs_prev` have no entries at all in `gold_layer_definitions_manual.py` — there's no column-level documentation for these tables in the codebase today.

## 8. Historic Backfill & the Manual/Scheduled Union Mechanism (`efront_specific/`)

- **"Union"/"unify"** = combining a one-time historic backfill table (e.g. `aum_asset_historics`) with the ongoing API-ingested snapshot table (`aum_asset_quarterly_snapshots`) into one logical table, via `unify_tables()` in `common/funcs/utils.py`. It uses `unionByName(..., allowMissingColumns=True)` then **fully overwrites** the target — this runs fresh on every single pipeline execution, not incrementally.
- **The historic tables self-heal.** `ensure_historic_tables_exist()` runs before the union and checks whether the prefixed historic table already exists; if not, it auto-triggers the corresponding `historic_*.ipynb` notebook via `dbutils.notebook.run(...)`. So the `historic_*.ipynb` notebooks are not purely "run once by hand" scripts — **any brand-new dev sandbox (new `{username}_` prefix) will automatically regenerate historic tables on first run.**
- **⚠️ The actual source-of-truth for historic data lives outside the repo, on SharePoint.** Each `historic_*.ipynb` notebook reads a fixed CSV path from a Unity Catalog Volume (e.g. `/Volumes/oegen_data_prod_prod/efront_landing/historics/Historic_AUM_Asset_DL.csv`), and links in a markdown cell to a source SharePoint spreadsheet (`Historic_TR_DL.xlsx`). **To update historic data:** someone must edit that SharePoint spreadsheet, re-export to CSV, re-upload to the fixed Volume path, and either manually re-run the notebook or drop the historic table so auto-heal regenerates it. There is no "force refresh" flag — the only trigger for regeneration is table absence.
- **Scheduled union only self-heals AUM history, not track-record history** — `union_parameters_scheduled.py`'s `historic_notebook_map` only covers `aum_asset`/`aum_fund`; track-record historic tables rely on the manual job or pre-existing tables.
- **Onboarding a new fund with pre-pipeline history** or doing a full historical reload both require this same manual dance: edit the SharePoint source, refresh the CSV, then either run the notebook directly or delete the table to let auto-heal do it.

## 9. Pipeline-Wide Configuration & Control

- **`DEVELOPMENT_PREFIX`** is the single mechanism that isolates dev/staging/prod without separate codebases. `pipeline_parameters.py` has been retired — `databricks.yaml` is now the sole source of truth for this value, and each notebook/module reads it directly for itself: notebooks via `dbutils.widgets.get("development_prefix")` (populated from job `base_parameters`), DLT library modules (`bronze_dlt_load.py`, `silver_dlt_load.py`) via `spark.conf.get("xio.development_prefix", ...)` (populated from the pipeline's `configuration:` block), and the two plain `.py` config modules (`cdm_checker_configuration.py`, `silver_aum_metrics_enriched.py`) via the shared `get_bundle_param(...)` helper in `common/funcs/bundle_params.py`. Values set in `databricks.yaml`: **staging and prod both use an empty string `''`**; `dev_test` uses `${workspace.current_user.short_name}_` (a per-developer prefix so multiple devs don't collide). Ad-hoc/unwired notebook runs (`historic_*.ipynb`) fall back to a static `"dev_"` widget default rather than sniffing the running user's email.
  - The `if DEVELOPMENT_PREFIX == "production":` checks that used to gate the PROD vs DEV `xio-common-functions` workspace path were dead code (staging/prod set `development_prefix` to `''`, never the literal string `"production"`) — these have been fixed to check `BUNDLE_TARGET == "prod"` instead, which `databricks.yaml` exposes via a `BUNDLE_TARGET` widget/`spark.xio.bundle_target` conf on every relevant task/pipeline.
  - `cd-efront-prod-deploy.yml`'s vestigial `sed` step (which tried to replace `DEVELOPMENT_PREFIX = 'dev_'` with `'production'` in `pipeline_parameters.py`) has been removed — it was already a no-op, and its target file no longer exists.
- **Catalog/schema defaults**: each consumer now widget-defaults these itself (e.g. `dbutils.widgets.text("DATA_CATALOG", "oegen_data_prod_test")`, `dbutils.widgets.text("LANDING_SCHEMA", "efront_landing")`, and similarly for `BRONZE_SCHEMA`/`SILVER_SCHEMA`/`GOLD_SCHEMA`) rather than importing them from a central `pipeline_parameters.py`. **These are only safe because `databricks.yaml` always overrides `DATA_CATALOG` per target** (`dev_test`→`oegen_data_prod_test`, `staging`→`oegen_data_prod_source`, `prod`→`oegen_data_prod_prod`) and passes every schema through `base_parameters`/`configuration:`. Any ad-hoc/local run bypassing the bundle silently defaults to writing into the **test** catalog — worth knowing before running anything standalone.
- **`FULL_REFRESH`** was hardcoded `False` in the now-deleted `pipeline_parameters.py` and was **not actually read anywhere** in this pipeline (unlike sibling pipelines gems/sennen/xio_operational_kpi, where it gates full-vs-incremental logic). In eFront, the equivalent behavior is achieved unconditionally instead: `databricks.yaml` sets `full_refresh: true` on both the bronze and silver DLT pipeline tasks — **every eFront run, manual or scheduled, is already a full refresh.** There's no flag a human ever needs to flip for this.
- **The manual/scheduled split is the pipeline's core operating pattern, repeated at every layer** via paired parameter files and paired jobs (`xio_efront_manual`/`xio_efront_scheduled`, `bronze_pipeline_manual`/`scheduled`, etc.). General rule observed: **scheduled = broad, automated, cadence-driven master data refresh; manual = targeted, human-triggered corrections/backfills** (e.g. manual ingestion touches only 2 AUM tables using `merge` for period-scoped corrections, vs scheduled's full `overwrite` of ~16 reference tables).
- **Deployment/CD — no manual approval gate exists.** `ci-efront-staging-test.yml` (PR → `staging`, touching `efront_pipeline/**`) runs `black` formatting (non-blocking), `databricks bundle validate/deploy -t staging` with retries, then a **placeholder test job that always passes** (no real test coverage today). `cd-efront-prod-deploy.yml` (push → `main`) runs `bundle validate/deploy -t prod` with retries, serialized via `concurrency.group: databricks-prod-workspace`. **Merging to `main` deploys straight to prod with no human sign-off step.**
- **Cron cadence (business-facing "when does this run"):**
  - Prod scheduled eFront job: **hourly, `:20` past the hour, 06:20–18:20 UTC, every day.**
  - Staging scheduled eFront job: **weekly, Sundays 07:20 UTC.**
  - Manual jobs (all environments): `schedule: null` — trigger-only, never run automatically.
  - Dev/dev_test: no schedule block at all — always manual trigger.
